# Issue #204: дефолтные типы доступа у сервиса + стандартное копирование

Статус: план от 2026-08-01; итерации 1–3 РЕАЛИЗОВАНЫ 2026-08-01 (отметки ✅ ниже,
отклонения от плана — в примечаниях итераций).

## Контекст

Учёт доступов (в первую очередь временных, через VPN) ведётся связкой
Schedules («временный доступ») → Acls (ресурс) → Aces (субъекты + типы доступа).
Ответственный регулярно оформляет один и тот же согласованный комплект:
RDP к терминалам + HTTPS к порталу + ВКС и т.п. Issue #204 просит, чтобы при
выборе сервиса галочки типов доступа предзаполнялись «типовым» для сервиса
набором.

Обсуждение расширило задачу:

1. **Дефолтные типы доступа — свойство сервиса** (аналог `ip_params_def` у
   AccessTypes, этажом выше). Полезно и как предзаполнение, и как документация
   «как ходят в этот сервис».
2. **Копирование — общий функционал базовых классов**: сценарии повторного
   создания похожих записей есть у многих моделей (пролонгация Contracts,
   продление LicItems/LicKeys, повторные закупки Materials, партия однотипных
   Techs, похожий Services, типовые MaintenanceReqs).
3. **Шаблон комплекта доступов = временный доступ-образец**: глубокая копия
   временного доступа с подменой субъекта и сроков покрывает и «повторить
   прошлую служебку», и «шаблоны» (временный доступ без реального субъекта,
   названный, например, «VPN Access template»).

Опорные факты по коду:

- `ArmsBaseController::actionCreate()` уже умеет предзаполнение формы из GET
  (`$model->load(Yii::$app->request->get())`).
- `linksSchema` объявлена у ~44 моделей — машиночитаемая карта прямых
  (`*_ids`/`*_id`) и обратных связей; generic-копия может по ней отличить,
  что переносить.
- Пикер типов доступа в форме ACE (`views/aces/_form_layout.php`) уже ходит в
  `access-types/access-types-form` (`AccessTypes::bundleAccessTypes()`) и умеет
  дочекивать/блокировать дочерние типы — предзаполнение от сервиса встраивается
  в тот же поток.
- `Aces::copyContentTo()` уже копирует содержимое ACE (субъекты, типы,
  ip_params из junction) — используется группами ACL.
- Валидатор ACE «хотя бы один субъект» (`validateRequireOneOf`) означает, что
  бессубъектный шаблонный ACE в лоб не сохранится — диалог копирования должен
  спрашивать субъекта, а шаблон может жить с заглушкой в `comment`.

## Итерация 1. Дефолтные типы доступа у сервиса (собственно issue #204) — ✅ СДЕЛАНО

### БД

- ✅ Миграция `M260801120000CreateDefaultAccessInServices`: junction-таблица
  `default_access_in_services` через `createMany2ManyTable` **без FK** —
  отклонение от плана: конвенция после `M251221163631ClearFk` (FK junction-таблиц
  выпилены; с FK генеративный REST-тест DELETE services падал на 1451).
  Дамп `tests/_data/arms_demo.sql` регенерирован (CI миграции не применяет).

### Доработка: сервисные IP-параметры дефолтных типов — ✅ СДЕЛАНО

Кейс: сервис предоставляет стандартный тип доступа на нестандартном порту
(PUPPET — HTTPS на TCP 8140). Вместо JSON-поля на сервисе — колонка `ip_params`
в junction (в точности как в `access_in_aces`): параметры — свойство связи
«сервис×тип». Реализация:

- виртуальный атрибут `Services::defaultIpParams` (зеркало `Aces::ipParams`:
  getter из junction, setter с merge, updater LinkerBehavior пишет в junction;
  пустая строка = «переопределения нет», действует `ip_params_def` типа);
- пикер типов доступа из формы ACE вынесен в общий партиал
  `views/access-types/_picker.php` (фильтр, инпуты IP-параметров) и
  переиспользован формой сервиса в режиме override (значение инпута — только
  переопределение, дефолт типа в placeholder); карточку-обвязку (заголовок =
  label атрибута из attributeData + иконка «?») партиал рисует сам
  (опции `card`/`label`);
- рукописный quick-add выпилен: кнопка «+» открывает ШТАТНУЮ форму AccessTypes
  в модалке (`open-in-modal-form`); в обработчик модалки (layouts/main.php)
  добавлен generic-хук `data-call-on-submit` — вызов именованной JS-функции
  с ответом сервера (пикер добавляет созданный тип в список отмеченным);
- предзаполнение отдаёт сервисные параметры вместо дефолтов типа: server-side
  (`AcesController::actionCreate` → `setIpParams`, с фиксом порядка кэш/isNewRecord
  в `Aces::getIpParams`) и в групповой форме (`services/default-access-types`
  теперь возвращает карту `{id: {ip_params}}`).

### Модели

- `Services`:
  - `linksSchema['default_access_types_ids'] => [AccessTypes::class, 'loader'=>'defaultAccessTypes']`;
  - relation `getDefaultAccessTypes()` через viaTable;
  - `attributeData`: подпись «Типы доступа по умолчанию», hint в духе
    «Какие типы доступа обычно предоставляются при выдаче доступа к этому
    сервису. Предзаполняют галочки в форме записи доступа (ACE); их всегда
    можно снять/добавить вручную»;
  - поле в форму сервиса (select2 multiple).
- `AccessTypes`: обратная связь в linksSchema (`default_services_ids`) — только
  схема, в UI не выводим.

### Предзаполнение форм

- **ACE в существующем ACL** (`AcesController::actionCreate`, GET `acls_id`):
  сервер: если ACE новый, `access_types_ids` пуст и у ACL ресурс — сервис с
  непустыми дефолтами → проставить `access_types_ids` до рендера. Дальше
  штатный `updateAccessTypes()` сам дочекает дочерние типы и параметры.
- **Групповая форма создания ACL** (`AclsController::actionCreate`, ресурсы
  выбираются в той же форме): JS — при изменении мультиселекта
  `Acls[services_ids]` дергать новый endpoint
  `services/default-access-types?ids[]=…` (union дефолтов выбранных сервисов),
  дочекивать галочки (НЕ блокировать) и вызывать `updateAccessTypes()`.
  Предзаполнение не срабатывает, если пользователь уже трогал галочки руками
  (не перетирать ручной выбор).
- Единичный `services_id`, переданный в GET (ссылки «создать доступ» со
  страницы сервиса), покрывается серверным путём.

### Тесты

- Генеративные: формы/эндпоинты покроются автоматически (`testCreate` и т.п.);
  новому action `default-access-types` — свой `testDefaultAccessTypes()`.
- Целевой: сценарий в `AcesController::testCreate()` — ACL с сервисом, у
  сервиса дефолтные типы → в отрендеренной форме чекбокс типа checked.

### Help

- `docs/help/services.md` и хинты: описать назначение поля (element-locality:
  описание атрибута живёт на нём).

## Итерация 2. Generic «Копировать» в базовых классах (мелкое копирование) — ✅ СДЕЛАНО

Примечания реализации:
- фильтр «обратных ссылок» — только *_ids, чья обратная сторона `*_id`
  (дети one-to-many); симметричные m2m переносятся (ArmsModel::copyPrefillAttributes);
- `copySupported()`: при кастомном actionCreate копия включается переопределением
  `copyViewParams()`/`actionCopy()`, иначе GET copy редиректит на create;
- кнопка (CopyObjectWidget) рендерится LinkObjectWidget только на странице самого
  объекта (samePage); для контроллеров за URL-алиасами модулей — явный `showCopy`;
- `testCopy()` в базовом контроллере с guard'ами (нет modelClass / нет full-модели /
  копия не поддерживается → сценариев нет).

### ArmsModel

- `copyPrefillAttributes(): array` — список атрибутов для переноса в копию:
  - safe-атрибуты сценария default минус PK;
  - минус readOnly-атрибуты (`attributeData['readOnly']`);
  - минус пер-модельные исключения `$dontCopyAttrs` (уникальные/инвентарные:
    num, sn, uid, external-идентификаторы синхронизаций и т.п.);
  - прямые связи из linksSchema (`*_ids` многие-ко-многим и `*_id`) входят,
    обратные (children/loader-обратки) — нет.
- `copyPrefillFrom(ArmsModel $source): void` — переносит значения по этому
  списку в несохранённую модель.

### ArmsBaseController

- `actionCopy(int $id)`: находит образец, создаёт новую модель,
  `copyPrefillFrom()`, рендерит штатную create-вьюху (POST уходит в обычный
  `actionCreate`). Серверное предзаполнение вместо GET-ссылки — чтобы не
  упереться в длину URL (notepad, ips).
  Доступ — как у create (PERM_EDIT-модель).
- `testCopy()`: сценарий 'form load' (GET id=full→200) — авто-покрытие всеми
  контроллерами через PageAccessCest.
- Возможность выключить: `disabledActions()` уже есть; плюс дефолтный опт-аут
  для моделей, которыми управляет синхронизация (Users) — им копия не нужна.

### UI

- Кнопка «Копировать» в стандартной обвязке карточки (рядом с
  редактировать/удалить в `LinkObjectWidget` — уточнить точное место при
  реализации), показывается при праве на создание и не-disabled action.

### Тесты

- Юнит на `copyPrefillAttributes()` для пары показательных моделей
  (перенос *_ids, исключение PK/readOnly/`$dontCopyAttrs`);
- генеративные — бесплатно через `testCopy()`.

## Итерация 3. Глубокая копия временного доступа (комплекты и шаблоны) — ✅ СДЕЛАНО

Примечания реализации: ScheduledAccessController::actionCopy + вьюха copy.php
(форма: имя/заметки + необязательная подмена субъектов-пользователей); периоды
образца не копируются; тест — сценарии form load / copy post с ассертом по БД
(вместо отдельного юнита: генеративный сценарий покрывает транзакционное
копирование целиком). Руководство docs/help/guides/temporary-access.md дополнено
разделом «Копирование и шаблоны».

### Сценарий

Кнопка «Копировать» на странице временного доступа (`scheduled-access/view`)
→ форма: название нового доступа, сроки (поля расписания), субъект(ы)
(users_ids; опционально другие виды субъектов). Сабмит: в одной транзакции

1. клон Schedules (+ его записи расписания/период);
2. на каждый ACL образца — новый ACL с тем же ресурсом и notepad;
3. на каждый ACE — новый ACE через `copyContentTo()` с **подменой субъектов**
   на указанных в форме (ip-субъекты образца при подмене очищаются);
4. редирект на страницу нового временного доступа.

### Шаблоны (вырожденный случай)

- Шаблон = временный доступ-образец без реального субъекта: в шаблонных ACE
  субъект-заглушка в `comment` (валидацию не трогаем) либо тестовый субъект.
  Отдельной сущности «шаблон» не заводим: имя вида «Шаблон: …» + копирование
  дают весь функционал. Если обкатка покажет потребность — признак
  is_template/фильтр добавим следующей итерацией.

### Тесты

- Юнит `ScheduleDeepCopyTest`: образец с 2 ACL × ACE (в т.ч. ip_params в
  junction) → копия эквивалентна по сигнатурам (`aceSignature()` с поправкой
  на подменённых субъектов), транзакционность (ошибка на середине — ничего
  не создано);
- acceptance-сценарий на новый action.

### Явно вне объёма

- Автоматика фаервола/AD по дефолтным типам — учёт остаётся учётом.
- Композитные «роли» поверх типов доступа — уже есть иерархия AccessTypes.
- Отдельный справочник шаблонов — см. выше, пока не нужен.

## Порядок

Итерации независимы по коду (1 — про формы доступов, 2 — про базовые классы),
но 3 опирается на UI-паттерн кнопки из 2, поэтому порядок: 1 → 2 → 3.
Каждая итерация выкатывается и обкатывается отдельно.
