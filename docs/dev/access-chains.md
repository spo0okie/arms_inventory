# Доступы как граф связей: DNS-имена, пробросы, транзит, сегменты

Реализованная работа по issues #219 (NAT-пробросы и внешние DNS-имена) и
#220 (матрица межсегментного доступа). Здесь — как это устроено и почему
именно так; пользовательская сторона описана в справке:
[aces.md](../help/models/aces.md) (транзит, пробросы),
[dns-names.md](../help/models/dns-names.md),
[segments.md](../help/models/segments.md) (матрица),
[руководство «Контроль доступа»](../help/guides/access-control.md).

## 1. Главные тезисы

**Цель** — развитие механизма документирования межсервисных связей до
транзитных из нескольких хопов. Потребитель — **ответственный за сервис**,
которому надо явно записать «мой сервис ходит в другой *через* прокси»;
раньше это жило в комментариях («приходит на порт 44344, который в описании
сервиса указан как порт для ERP PROD»). Сознательно **не** потребители:
сетевик (ему для настройки ACL хватает одного хопа, вся цепочка — бонус) и
ИБ с «потоками данных между ИС» (запроса не было, строить впрок
нерационально).

- **ACL/ACE — механизм документирования связей, а не только прав.**
  «Сервис А требует доступ к сервису Б по протоколу В с сетевыми
  параметрами Г» ≡ сетевой доступ всех узлов А к узлам Б. Поэтому NAT,
  транзит и межсегментная политика выражаются теми же записями доступа —
  без новых сущностей: иначе платим кодом за рост стоимости документирования.
- **Информация о маршруте живёт в связях.** Поток «Документооборот → прокси
  :44344 → ERP :443» не хранится, он вычисляется из записей доступа,
  связанных указателем «следующий хоп». Хоп — это ACE (пара «субъект →
  ресурс»), а не ACL.
- **Всё, что ортогонально справочнику, вешается на хоп, а не на запись
  справочника.** Признак проброса — свойство записи доступа, а не типа
  доступа (см. §3: попытка с флагом на типе не пережила первого дня обкатки).
- **Имя относится к узлу через адрес.** DNS-имя указывает на IP, а к какому
  узлу и сервису оно относится — выводится: имя → IP → ОС/оборудование →
  сервис. Собственных ссылок на узлы и сервисы у имени нет.
- **Узел-посредник не описывается.** Где настроен NAT, какой nginx держит
  маршрут — не учитываем: маршрутизаторы тут Debian-VM (то есть ОС, а не
  оборудование), белый адрес и так привязан к ОС роутера через
  `ips_in_comps`; облачный NAT, где белый IP ни к чему не привязан,
  описывается комментарием.

### Отвергнутые варианты

Записаны, чтобы к ним не возвращаться.

| Вариант | Почему нет |
|---|---|
| Отдельная сущность «Проброс» (`nat_rules`: вход IP:порт → назначение IP:порт) | Описывает поведение узла-посредника — это нужно сетевику и ИБ, а не цели. Вторая модель для того, что уже выражается записью доступа |
| Связи между ACL | Хоп — это ACE: у одного ACL несколько записей с разными субъектами и портами, маршруты у них разные |
| Сопоставление хопов по портам (порт входящего ACE ↔ порт правила) | `ip_params` — свободный текст; эвристика ненадёжна. Указатель ставит человек, неоднозначность «ACL говорит "может", а не "ходит"» снимается им же |
| Флаг проброса на типе доступа (`access_types.is_forward`) | Был реализован и отвергнут обкаткой: пришлось бы дублировать каждый тип («HTTPS forward», «RDP forward»…) — проброс ортогонален протоколу |
| Вывод проброса из стрелки в параметрах (`TCP 443->8443`) | Проброс без смены порта стрелки не имеет; неявные признаки в данных — источник расхождений |
| `comps_id`/`techs_id` у DNS-имени | Дублировали бы hostname узла почти в чистом виде (добавился бы только комментарий) |
| `services_id` у DNS-имени | Сервис выводится через адрес и узел |
| Признак «внешняя зона» (`is_external`) у домена | Доменов меньше десяти, какой из них внешний — известно; список внешних имён — это карточка внешней зоны |
| Сторож «DNS-имя совпало с hostname узла» | Привязки и так широкие (многие-ко-многим, имена без адресов) — запрет лишний |
| Текстовое поле DNS-имён на записи проброса | Имена — отдельные записи на белом адресе; цепочка связна в обе стороны без текста |
| Развитие `Services.depends_ids` до графа отказов | Нет степени зависимости (ляжет / деградирует / проживёт на кэше); бесполезно уже на 50 сервисах. Поле оставлено как есть |

## 2. DNS-имена

`DnsNames` — «имя в зоне → набор IP». Зона — существующий справочник
`Domains`: он и так DNS-зона (NetBIOS-имя + fqdn). Hostname узлов
(`Comps.name`, `Techs.hostname` + домен) остаются каноническими именами —
на них завязаны AD-синк, песочницы и уникальность; `DnsNames` описывает то,
чего у узла нет: алиасы, имена сервисов на реверс-прокси, имена на белых
адресах без узла.

- **Колонка `host`, а не `name`.** `name` в ARMS — подпись объекта (ссылки,
  `ItemColumn`, item-by-name), а подпись имени — полное имя. Поэтому левая
  часть хранится в `host`, подпись — calc `fqdn` через `$nameAttr`
  (`DnsNamesModelCalcFieldsTrait`, общий с журналом; зона берётся из кэша
  справочника). Пустой `host` — запись на саму зону (apex).
  Базовый `ArmsBaseController::findByName()` ищет по колонке `name`, поэтому
  в `DnsNamesController` он переопределён на `DnsNames::findByName()`.
- **Разбор полного имени** — `Domains::splitFqdn()`: из зон, чей fqdn
  совпал с хвостом имени (или с именем целиком — apex), берётся самая
  длинная. `Domains::fetchFromCompName()` для этого не годится — он режет по
  первой точке (у hostname точек нет, у DNS-имён бывают). Фильтр `host` в
  `rules()` стоит **до** `required` у `domain_id`: ввод `www.example.com`
  сам выставляет зону.
- **Адреса — как у оборудования:** реальная колонка `ip` (текст, по одному в
  строке) плюс junction `dns_names_in_ips`; в `beforeSave` —
  `NetIps::fetchIpIds()` (адреса создаются на лету), отвязанные адреса
  проходят `NetIps::detachDnsName()`, после удаления имени — `deleteIfEmpty()`.
  Источник истины связи имя↔адрес — текстовое поле имени, поэтому привязка
  «с адреса» (`dns-names/attach-ip`: одно поле — выбрать готовое имя или
  ввести новое) тоже идёт через сохранение имени. Пустой набор адресов
  допустим: имя заведено, но ни на что не указывает.
- `NetIps::deleteIfEmpty()` учитывает DNS-имена: адрес, на который указывает
  имя, сам из реестра не уходит.
- Связь с адресами объявлена `'deletable'=>true` (как `netIps_ids` у ОС):
  иначе сторож удаления считает адреса «держащими» имя и прячет корзину.
- **Карта зоны** — `views/domains/zone.php` на карточке домена: единый
  список из трёх источников (ОС, оборудование, DNS-имена) по имени, с
  иконкой типа и адресами; связи грузятся жадно, в тултипе домена не
  рендерится. Это и есть «список внешних имён» (сценарий: поставить TLS на
  мониторинг истечения) — достаточно открыть карточку внешней зоны.

## 3. Пробросы (NAT, реверс-прокси)

Проброс — обычная запись доступа с признаком **`aces.is_forward`**:
субъект — адрес входа (белый IP), ресурс ACL — узел назначения или его
адрес, сетевые параметры типа доступа — `порт входа -> порт назначения`
(`TCP 443->8443`; без стрелки порт не меняется). Типы доступа остаются
обычными: HTTPS, RDP, Ovpn.

- Разбор параметров — `Aces::parseForwardParams()` (`->`, `=>`, `→`).
  Правила проброса записи — `getForwardRules()`: по одному на каждый
  IP-тип; запись-проброс без IP-типов даёт одно правило без портов —
  проброс всё равно должен быть виден.
- Выборки — `Aces::findForwardsTo(ОС, оборудование, адреса)` и
  `findForwardsFrom(адреса)`: условие по флагу записи, жадная загрузка
  `Aces::FORWARDS_WITH`, архивные (мёртвый ресурс, истёкшее расписание)
  отбрасываются.
- Показ — один вью на всех, `views/aces/forwards.php`: строка «адрес входа
  (DNS-имена) параметры → назначение :порт», стрелка — ссылка на саму
  запись. Блоки: «Доступен снаружи» у ОС и оборудования (`forwardsIn` — на
  узел или его адреса), «Пробрасывается на» и «Доступен снаружи как» у
  IP-адреса, «Пробрасывается на» у DNS-имени (по всем его адресам — цепочка
  имя → адрес входа → узел). Когда назначение задано адресом, рядом
  выводится узел-владелец.
- Блоком, а не значком у каждого IP: строка читается сама, значку нужен был
  бы тултип.
- Белый адрес как субъект ACE уже учитывался в `NetIps::deleteIfEmpty()` —
  под NAT там ничего не менялось.
- Флаг входит в сигнатуру ACE (групповые ACL сравнивают записи по ней) и в
  копирование записи; проброшенный хоп помечен значком на карточке ACE и в
  маршрутах.
- **Известный пробел:** L7-прокси, раздающий N имён на N бэков, — «какое имя
  куда» на уровне связей не выражается (входящий проброс один, следующих
  хопов несколько). Не моделируется; при нужде — опциональная ссылка
  DNS-имя → ACE «имя обслуживается этим хопом».

## 4. Транзит: маршрут из нескольких хопов

Junction `aces_next_aces (aces_id, next_aces_id)`. Редактируются **обе
стороны** одной таблицы — `next_aces_ids` и `prev_aces_ids` (образец —
includes/included у `MaintenanceReqs`): ответственному за конечный сервис
удобнее сказать «это продолжение вон того входящего», чем идти в чужую
запись. Многие-ко-многим: у одной записи несколько типов с разными портами
уходят в разные апстримы, а несколько входящих сходятся в один исходящий.
Обе связи `deletable` — маршрут документация, удалению записи не мешает.

- **Сторож циклов** — `Aces::validateTransitLink()` поверх
  `validateRecursiveLink` в обе стороны (с `initialLink` — ссылки проверяются
  до записи в БД).
- **Кандидаты в хопы подбираются по посреднику**, а не из всех ACE системы:
  `nextCandidates()` — записи, где субъект — ресурс этой записи (сервис с
  предками и потомками, узлы ресурса и их адреса); `prevCandidates()` —
  записи доступа к субъектам этой записи. У записи без ресурса/субъектов
  список пуст до первого сохранения.
- **Маршруты:** `Aces::transitEdges()` — все рёбра одним запросом на
  веб-запрос (маршрут дергается на каждую строку списков, а транзита у
  подавляющего большинства нет), сброс в `afterSave`/`afterDelete`;
  `getRouteIds()` собирает полные пути через запись (вверх × вниз),
  `routesOf()` грузит хопы всех маршрутов пачки одним запросом
  (`Aces::ROUTES_WITH`). Страховки — `ROUTES_LIMIT` (ветвления
  перемножаются) и `ROUTE_DEPTH_LIMIT` (на случай цикла, заведённого мимо
  валидации).
- **Мягкая проверка стыка** — `Aces::transitJoint()`: есть ли ресурс
  предыдущего хопа (или его узлы) среди субъектов следующего. Не запрет
  (субъект бывает шире — сеть, сегмент), а значок предупреждения в маршруте.
- **Показ** — `views/aces/routes.php`: «субъекты первого хопа →[тип: порты]
  ресурс →[…] ресурс», стрелки — ссылки на ACE хопов, текущий хоп выделен
  (у посредника видно транзитные соединения, у конечного сервиса — кто
  приходит через посредника). Колонка `transit` («Маршрут») в гридах ACE и
  ACL плюс блок на карточке ACE; `getTransit()` — те же маршруты текстом.
- Self-join таблицы `aces` — **только с алиасом** (`next_aces`,
  `prev_aces`): без него падает `joinWith` поиска. По той же причине у
  колонки маршрута нет `join`-аннотации — она считается из кэша рёбер.

## 5. Уровни показа доступов

Гриды ACE и ACL несут колонки двух уровней: информационного (субъекты,
ресурс, маршрут — кто к чему и каким путём) и сетевого (узлы с адресами —
что нужно для настройки ACL на один хоп). `AccessLevelSwitchWidget` прячет
колонки чужого уровня классом на `body` (действует и на асинхронно
подгружаемые вкладки), выбор хранит в `localStorage`. Таблица «какая колонка
к какому уровню», механика меток и порядок добавления новой колонки
расписаны в докблоке самого класса — он первоисточник. Стоит на страницах
сервиса и IP-адреса и во вкладке сети «Вх. соединения».

Механизм опирается на то, что ячейка данных и ячейка фильтра всегда несут
класс `<атрибут>_col`: `DefaultColumn` дожимает его в ячейку даже при
contentOptions-замыкании, `DynaGridWidget::defaultColumn` дописывает в
`filterOptions`.

## 6. Сегменты в доступах и матрица

Сегмент — ресурс ACL (`acls.segments_id`) и субъект ACE (junction
`segments_in_aces`). Имя колонки — по образцу соседних ресурсных колонок
ACL (`comps_id`…`networks_id`), пары `*_id ↔ *_ids` групповой формы
(`AclsController::GROUP_RESOURCE_MAP`) и сегмента у `Networks`. Relation —
`Acls::getSegment()`; вычисляемое `Acls::getSegments()` (сегменты, где
расположен ресурс) осталось и понимает сегмент-ресурс.

- **Развёртка одна для ресурса и субъекта** — `Segments::getAccessNodes()`:
  объект доступа — сам сегмент, узлы доступа — его подсети и узлы его
  сервисов (`nodesRecursive`).
- **У сегмента есть архивность:** `segments_resources.archived` входит в
  `Acls::aliveResourceCondition()`, `segments.archived` — в
  `Aces::aliveSubjectsCondition()`; доступ к архивному сегменту (и от него)
  архивный, матрица по умолчанию без архивных сегментов (`?showArchived=1`).
- **Матрица** — `Segments::accessMatrix()` + `/segments/matrix`: строки —
  откуда, колонки — куда, запись в ячейке — ссылка на ACE. В неё входят
  **только** ACL с ресурсом-сегментом и ACE с субъектом-сегментом:
  - доступ, нацеленный на конкретный узел/сервис/сеть сегмента, матрицу не
    интересует — он виден во вкладке сети «Вх. соединения»;
  - доступ к сегменту от несегментного субъекта (сервис, сеть, адрес)
    матрица игнорирует — сегмент субъекта косвенно не выводится; такой
    доступ виден на странице сегмента.
- **Страница сегмента** — вкладки «Входящие доступы»/«Исходящие доступы»:
  грид ACE с фильтрами `AcesSearch::$segments_resource_ids` /
  `$segments_subject_ids`. Фильтры — подзапросами: набор join'ов в списках
  плавает от видимых колонок (`prepareSearch`), подзапрос от него не зависит.
  Так же устроены вкладки доступов на странице IP-адреса
  (`$ips_resource_ids` / `$ips_subject_ids` — сам адрес или узлы, к которым
  он привязан).
- **Вкладка сети «Вх. соединения» существовала** —
  `Networks::getIncomingAcesEffective()` собирает ACE сети, её адресов,
  узлов и сервисов; к ним добавлены доступы к сегменту сети (`Segments`
  получил `AclsFieldTrait`). Отдельная вкладка не заводилась.
- Доступ пользователей к сервисам решается тем же слоем: у сервиса объявлен
  сегмент, матрица показывает, из каких сегментов он достижим.

## 8. Готчи

- **Дамп до тестов.** Полный unit-набор посреди прогона перезаливает
  `tests/_data/arms_demo.sql` (`ApiSchemaResolvableTest`): новые таблицы
  должны быть в дампе до запуска, иначе у тестов новой сущности «table does
  not exist».
- **Junction в сидах — только с явными id.** Без них повторный прогон
  сидов даёт другие автоинкременты, и дамп «плавает».
- **Статические кэши сбрасывать при записи.** Рёбра транзита
  (`Aces::resetTransitCache()`), иерархия типов доступа
  (`AccessTypes::invalidateAllItemsCache()`): в тестах и POST-экшенах запись
  и чтение идут в одном процессе.
- `Acls::getSname()` не знал ресурс-сеть (подпись «ресурс не задан») —
  ветка добавлена вместе с сегментом.

  механизм [интеграций](integrations.md) — сверка с записями-пробросами.
- Сверка DNS-имён с живым DNS (resolve → адреса имени) и срок
  TLS-сертификата у имён с пробросом на 443.
- Ссылка DNS-имя → ACE для L7-прокси (см. пробел в §3).
- CNAME-цепочки (имя → имя → CDN): nullable-ссылка имени на родителя.
- Более широкие потребители маршрутов (карта, экспорт, потоки данных для
  ИБ) — только по явному запросу.
