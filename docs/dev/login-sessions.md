# Сессии пользователей в журнале входов (для разработчиков)

Журнал входов (`login_journal`) хранит не только событие входа, но и
**сессию с окончанием** — для записей, которые присылает служба
инвентаризации Windows (arms.winservice, соседний репозиторий). Здесь —
серверная часть: хранение и приём. Требования и протокол со стороны службы —
в её ТЗ (`TZ.md`, §6–§7).

Состояние: приём реализован, отображение (блоки входов в карточках ОС и
сотрудника, фильтры журнала, ручное закрытие) — следующий этап.

## 1. Два вида записей

| | Старые скрипты (win-inventory) | Служба (arms.winservice) |
|---|---|---|
| `session_uid` | пусто | GUID сессии, уникален |
| Смысл записи | событие входа | сессия: начало и окончание |
| Окончание | неизвестно | `end_time`, `end_type` |
| Повторная доставка | 409 по окну времени ±5 с | upsert по ключу, безвредна |

**Открытая сессия** — запись с `session_uid` и без `end_time`
(`LoginJournal::getIsOpen()`, `LoginJournal::findOpen()`). Записи без ключа
открытыми не считаются: об их окончании ничего не известно. Поэтому прежняя
история журнала миграции данных не потребовала.

## 2. Поля

| Поле | Смысл |
|---|---|
| `session_uid` | Ключ сессии, генерирует служба |
| `time` / `calc_time` | Начало в часах клиента / в часах сервера (как и раньше) |
| `end_time` | Окончание в часах сервера |
| `end_type` | Тип окончания, `LoginJournal::END_*` |
| `flags` | Битовая маска достоверности времени, `LoginJournal::FLAG_*` |
| `closed_by` | Кто закрыл сессию вручную (для `END_MANUAL`) |

Типы окончания 1–99 сообщает служба (`LOGOFF`, `SHUTDOWN`,
`SERVICE_STOPPED`, `SERVICE_CRASH`, `SYSTEM_STOP`), 100+ ставит сервер
(`LOST`, `MANUAL`).

Флаги — одно целое поле, а не столбец на флаг: по нему можно фильтровать в
SQL (`flags & 2`), а новые флаги не требуют миграции.

## 3. Приём сессии: `POST /api/login-journal/push`

Тело с `session_uid` обрабатывает `LoginJournalController::pushSession()`:
записи нет — создаётся, есть — обновляется по правилам
`LoginJournal::applySessionPush()`:

- **Начало пишется один раз.** Служба пересчитывает отметки в календарное
  время в момент каждой отправки, и от запроса к запросу начало плавает на
  погрешность доставки. Обновлять его — значит дёргать значение без смысла.
- **Окончание от службы тоже пишется один раз.**
- **Окончание от сервера (`LOST`, `MANUAL`) — догадка.** Данные службы его
  перезаписывают: и реальное окончание, и «сессия на самом деле открыта».
- Запоздавшее «сессия открыта» не открывает сессию, закрытую службой.

Тело без `session_uid` — прежнее поведение без изменений.

## 4. Время

Служба присылает отметки в своих часах (unix) и `local_time` — свои часы на
момент отправки. Если `local_time` расходится с часами сервера больше
`LoginJournal::$maxClockSkew` (90 с), отметки сдвигаются на это расхождение
(`LoginJournal::correctClientTime()`). Так было для `calc_time`; теперь то
же применяется к `end_time`.

Порог нужен, потому что в расхождение входит время доставки. Окончание в
будущем (после сдвига) отклоняется, как и начало.

## 5. Список открытых сессий и heartbeat: `POST /api/comps/push`

- **`open_sessions`** — полный список ключей сессий, открытых на ОС. Служба
  присылает его в полном слепке. Открытые в журнале сессии этой ОС, которых
  в списке нет, закрываются как `LOST` (`LoginJournal::closeLost()`): служба
  о них не знает (потеряла локальное состояние, переустановлена), сами они
  уже не закроются. Пустой список закрывает все; отсутствие атрибута не
  закрывает ничего.
- **Heartbeat** — запрос без данных инвентаризации (только `id` и/или имя
  этой же записи). Обновляет только `updated_at` через `updateAttributes()`:
  полный `save()` на каждый heartbeat от каждого хоста — лишняя нагрузка, а
  история ОС это поле не журналирует. Запрос с прежним `id` и новым именем —
  не heartbeat, а переименование: идёт обычным обновлением.

`updated_at` ОС, таким образом, — ещё и отметка «хост на связи»: по ней
определяется, можно ли доверять открытым сессиям хоста.
