# Механизм интеграций с внешними ИС (для разработчиков)

Документация механизма подключаемых интеграций: показ живых данных из
внешних ИС в карточках объектов и выполнение действий во внешних ИС.
Здесь — архитектура и контракт для написания новых провайдеров.

Смежные документы:
- администрирование и включение на инстансе — [docs/help/admin/integrations/providers.md](../help/admin/integrations/providers.md);
- целеполагание и история решений — в git (планы `plans/integrations*.md`
  до переноса, коммиты августа 2026).

## 1. Зачем и что это

Поток задач вида «показать в карточке объекта ARMS данные из внешней
системы» и «выполнить действие во внешней ИС» (алерты Zabbix, статус
VoIP-номера, справка AD, отправка SMS, сброс пароля). Вшивать каждую
интеграцию в ядро — тупик: код обрастает ветками, интеграции нельзя
включать/дописывать без правки ядра.

Решение — **in-process плагины с единым контрактом**: ядро (реестр,
proxy, виджеты, кэш, RBAC, журнал) написано один раз; конкретная
интеграция — самодостаточный класс-провайдер. Ядро объектов и view-файлы
при добавлении новой интеграции не трогаются.

Все сценарии ложатся в схему из четырёх элементов:
1. **применимость** — к каким объектам ARMS относится;
2. **привязка** — как из объекта получить ключ во внешней ИС (атрибут
   или явная привязка в `external_links`);
3. **представление** — L0 ссылка / L1 панель чтения / L2 действие;
4. **авторизация** — от чьего имени идём во внешнюю ИС.

### Не-цели

Механизм не синхронизирует данные (не импортирует в БД), не хранит
историю внешних данных, не является шиной/ESB (только запрос-ответ по
инициативе ARMS) и не защищается от недоверенного стороннего кода
(провайдеры свои).

## 2. Авторизация

| Уровень | От чьего имени | Доступ | Примеры |
|---------|----------------|--------|---------|
| Чтение (L1) | Сервисная учётка ARMS во внешней ИС | RBAC-право на просмотр | Zabbix, телефония, AD-справка |
| Запись обычная (L2) | Сервисная учётка ARMS | RBAC-право + аудит | SMS |
| Запись именная (L2+) | **Личные** учётные данные исполнителя, запрошенные в момент действия | RBAC + ввод кредов на один запрос, без сохранения | Сброс пароля AD |

Принципы:
- **Все запросы идут через backend ARMS** (proxy). Браузер никогда не
  ходит во внешние ИС и не видит секретов. Внешние ИС можно держать в
  закрытых сегментах, доступных только серверу ARMS.
- **Секреты сервисных учёток** — только в `params-local.php` (как
  `sms.url`, ldap). В БД секретов нет.
- **Границу L2/L2+ задаёт внешняя ИС, а не ARMS.** Пока действие
  допускается под сервисной учёткой — оно L2 (прозрачно, аудит на
  стороне ARMS). Как только внешняя ИС требует идентификации живого
  исполнителя (сброс пароля в AD) — действие L2+, и пользователь вводит
  свои учётные данные этой ИС в момент действия (на один запрос).

## 3. Состав ядра

| Компонент | Место | Назначение |
|-----------|-------|-----------|
| `IntegrationProvider` | `components/integrations/IntegrationProvider.php` | Базовый абстрактный класс — контракт (§4) |
| `IntegrationsRegistry` | `components/integrations/IntegrationsRegistry.php` | Реестр из `params['integrations']`, проверки доступа, выполнение действий |
| `IntegrationsController` | `controllers/IntegrationsController.php` | Proxy: `/integrations/panel` и `/integrations/action` |
| `PanelsWidget` | `components/integrations/PanelsWidget.php` | Блок интеграций в карточке объекта |
| `AttributeActionsWidget` | `components/integrations/AttributeActionsWidget.php` | Действия-иконки у атрибута (SMS у телефона) |
| `PanelsCache` | `components/integrations/PanelsCache.php` | Файловый кэш панелей (`runtime/integrations_cache/`) |
| `ActionResult` | `components/integrations/ActionResult.php` | Результат действия (ok/HTML/logParams) |
| `IntegrationsLog` | `models/IntegrationsLog.php` | Журнал действий (таблица `integrations_log`) |

Провайдеры — `components/integrations/providers/<Name>Provider.php`,
их view — `components/integrations/providers/views/<id>/*.php`.

Конфигурация (инстанс включает своё в `params-local.php`):

```php
'integrations' => [
	'<id>' => [
		'class' => \app\components\integrations\providers\XxxProvider::class,
		// ... конфиг провайдера (секреты, url, ttl)
	],
],
```

Ключ массива = `id` провайдера. Ядро интерпретирует `class` и общие
опции (`cacheTtl`, `timeout`), остальное — дело провайдера.

## 4. Контракт провайдера

Базовый класс `IntegrationProvider` (полная сигнатура — в самом файле):

- `getTitle()`, `isConfigured()` — регистрация и самодиагностика
  (ненастроенный провайдер невидим);
- `appliesTo($model)` — применимость (по классу, вычисляемым признакам,
  атрибутам и/или собственному конфигу); **обязана быть дешёвой**,
  внешние запросы запрещены (вызывается при рендере каждой карточки);
- `binding($model)` — ключ привязки (атрибут или `external_links`; путь
  внутри JSON выбирает сам провайдер); `null` = применим, но не привязан;
- `panels($model)` — L1-панели `[panelId => ['title','ttl']]`;
- `renderPanel($panelId,$model)` — сходить во внешнюю ИС, вернуть готовый
  **HTML** (вызывается только из proxy, никогда при рендере страницы);
- `actions($model)` — L2/L2+ действия (`level`, `form`, `standalone`,
  `showInPanel`, `prefill`);
- `attributeActions($model,$attr,$value)` — действия-иконки у атрибута;
- `runAction($actionId,$model,$form,$credentials)` — выполнить действие
  (вызывается только через реестр — там журналирование).

Требования:
- **Транспорт любой** (HTTP, JSON-RPC, LDAP), но все внешние вызовы —
  только на сервере и только из `renderPanel()`/`runAction()`.
- **Таймауты обязательны**: `$this->timeout()` ко всем сетевым операциям.
- Недоступность внешней ИС — штатный исход (исключение ловит ядро,
  показывает заглушку, старый кэш не перетирается).
- Внешние вызовы выносить в отдельный метод (тесты подменяют его
  наследником, не трогая сеть) — так сделаны все провайдеры.

### Декларативный `HttpTemplateProvider`

Для тривиальных интеграций «одна панель по одному GET с JSON-ответом»
класс писать не нужно: применимость, запрос и рендер задаются целиком
конфигом. Границы: один GET, JSON-ответ, авторизация ключом в
URL/заголовке. Сложнее — полноценный класс. Опции — в docblock класса.

## 5. Потоки

### Панель чтения (L1) — stale-while-revalidate

1. `PanelsWidget` в карточке обходит реестр (включён + `isConfigured()`
   + RBAC + `appliesTo()`) и для каждой панели выводит контейнер с
   содержимым файлового кэша **приглушённо** — без обращений к внешним ИС.
2. Если кэша нет или он старше `ttl` — дописывается ajax-скрипт (паттерн
   `WikiTextWidget`): `GET /integrations/panel`, ответ подменяет
   содержимое и снимает приглушение.
3. Proxy: RBAC → модель → `binding()` → свежий кэш отдаётся как есть,
   иначе `renderPanel()` с таймаутом → запись в кэш → HTML.
4. Ошибка/таймаут: кэш не перетирается, в контейнер — компактная заглушка.

`ttl` панели управляет только тем, **пропускать ли обновление**, а не
показом: кэш рисуется мгновенно в любом случае. `ttl => 0` = «обновлять
при каждом открытии карточки» (данные всегда актуальны, кэш остаётся
буфером мгновенной отрисовки и подстраховкой на случай недоступности
внешней ИС). Ставить ttl > 0 стоит только там, где внешняя ИС медленная
или её нежелательно опрашивать часто.

Страница ARMS никогда не ждёт внешнюю ИС. Кэш — файлы
`runtime/integrations_cache/<provider>/<panel>/<hash(binding)>.html`,
свежесть по `filemtime`, запись атомарная (tmp+rename). Кэш **общий на
инстанс**: чтение идёт от сервисной учётки, персонализации нет; в панелях
не должно быть данных «по правам пользователя».

### Действие L2

Кнопка (`open-in-modal-form`) → `GET /integrations/action` рендерит форму
провайдера в модалку → POST валидирует и вызывает
`Registry::runActionForm()` → журналирование → результат в модалку.
`standalone`-действия доступны без объекта.

### Действие L2+ (именное)

Как L2, но ядро добавляет в форму блок личных учётных данных исполнителя.
Креды передаются в `runAction()` одним аргументом, используются на один
вызов, нигде не сохраняются; в журнал пишется только логин (без пароля).

### Композиция: провайдер вызывает провайдера

Одна интеграция может опираться на другую (сброс пароля AD → отправка
пароля через SMS → останов при неудаче → запись в AD). Правила:
- вызов серверный, через реестр:
  `IntegrationsRegistry::runAction($providerId, $actionId, $model, $params, $credentials, $parentLogId)`
  — тот же путь, что у proxy, поэтому валидация и журналирование
  срабатывают одинаково;
- **RBAC проверяется только у инициирующего действия** — вложенному
  вызову отдельное право не нужно;
- зависимость объявляется конфигом (id провайдера-поставщика),
  проверяется в `isConfigured()`;
- журнал: запись открывается **до** выполнения (`result='run'`), её id
  доступен провайдеру в `$this->activeLogId` и передаётся как
  `parentLogId` вложенных вызовов; закрывается итогом после. Побочный
  плюс — действие, уронившее процесс, остаётся в журнале со статусом run.

## 6. RBAC, журнал, встраивание в UI

- **Доступ**: следует ровно модели авторизации ядра
  (`params` useRBAC/authorizedView, docs/help/admin/setup.md) — панель =
  «просмотр», действие = «изменение». При `useRBAC=true` доступ даёт
  адресное право (`view-integration-<id>` / `edit-integration-<id>-<action>`,
  создаёт `yii rbac/init`) **ЛИБО глобальный зонтик** `view`/`edit` —
  ровно как в `ArmsBaseController::buildAccessRules()`, где на каждое
  действие заводятся правила и под глобальное, и под адресное право.
  Поэтому пользователю с глобальным `edit` доступны все действия
  интеграций, с `view` — все панели; адресные права нужны лишь для
  тонкой раздачи (например, только SMS хелпдеску без глобального edit).
  Префиксы view-/edit- заставляют
  `ArmsBaseController::customizeAccessPermission()` применить к ним те же
  правила, что и к обычным операциям (единый источник правды —
  `IntegrationsRegistry::checkAccess()`). Так в полностью открытом режиме
  интеграции открыты всем, при `authorizedView` — только вошедшим, при
  `useRBAC` — по явно выданному праву (просмотр открыт всем, если
  authorizedView выключен).
- **Журнал** `integrations_log`: каждое действие (и успех, и ошибка),
  шаги композиции связаны `parent_id`. Секреты (пароли, тексты SMS с
  паролями) не пишутся — состав определяет провайдер через
  `ActionResult::$logParams`. Просмотр в UI — read-only грид
  `IntegrationsLogController` (`/integrations-log/index`, пункт в
  админ-меню «шестерёнка»): фильтры по провайдеру/действию/результату/
  дате/инициатору, карточка записи со связанными шагами. Записи только
  читаются (create/update/delete отключены).
- **Встраивание**: `PanelsWidget` — в общий `layouts/view.php`
  (автоматически для карточек без индивидуального view) и в
  индивидуальные карточки (`techs`, `users`, `comps`, `net-ips`) по
  одной строке; `AttributeActionsWidget` — у «активных» атрибутов
  (телефоны в `users/mobile-phone.php`). Оба виджета generic — упоминаний
  конкретных интеграций в ядре нет.

## 7. Реализованные провайдеры

| id | Класс | Тип | Применимость | Внешняя ИС |
|----|-------|-----|--------------|-----------|
| sms | `SmsProvider` | L2-действие (иконки у телефонов + standalone-форма) | `Users` с телефоном | SMS-шлюз с URL-шаблоном |
| pbx | `HttpTemplateProvider` | L1-панель | `Techs` с `isVoipPhone` и номером | ast22-phones REST (`/api/v1/subscribers/status`) |
| ad | `AdUserProvider` | L1-панель (справка о учётке) | `Users` с логином AD | `LdapService` (ldaprecord) |
| ad-reset | `AdPasswordResetProvider` | L2+-действие (композиция с sms) | `Users` с логином AD | `LdapService::resetPassword()` — LDAPS-bind под кредами исполнителя |
| zabbix | `ZabbixProvider` | L1-панель (активные проблемы) + L0-ссылка | `Comps` и `Techs` | Zabbix JSON-RPC 7.x |

Конкретные конфиги включения — в
[docs/help/admin/integrations/providers.md](../help/admin/integrations/providers.md).

Провайдеры `ad`/`ad-reset` не работают с LDAP-библиотекой напрямую: они
ходят в AD через компонент [`app\components\ldap\LdapService`](../../components/ldap/LdapService.php)
(поверх directorytree/ldaprecord) — единственную точку приложения,
знающую о конкретной библиотеке. Живая диагностика — `yii ldap/*`.

### Привязка Zabbix ↔ инвентаризация (двусторонняя)

hostid узла Zabbix хранится в `external_links` объекта под ключом
`Zabbix.hostid`. Постоянную привязку ведёт скрипт синхронизации
[arms.zabbix](https://github.com/spo0okie/arms_zabbix): при заведении/
поиске узла в Zabbix он пишет hostid обратно в инвентаризацию
(`inventoryApi::setExternalLink()` → PUT `/api/<class>/<id>` с
`external_links`; инвентаризация мержит поверх существующих ключей,
не затирая `VMWare.*` и прочее — контракт покрыт
`tests/unit/models/ExternalLinksMergeTest`). `ZabbixProvider` читает
этот hostid; если он ещё не записан — делает разовый поиск по FQDN/имени
только для отображения (панели в БД не пишут).

## 8. Как добавить новую интеграцию

1. Класс `components/integrations/providers/XxxProvider.php` — наследник
   `IntegrationProvider` (или конфиг `HttpTemplateProvider`, если случай
   тривиальный).
2. View панелей — `components/integrations/providers/views/<id>/*.php`
   (провайдер отдаёт готовый HTML).
3. Внешние вызовы — в отдельном методе (для подмены в тестах).
4. Тест `tests/unit/components/integrations/XxxProviderTest.php` —
   транспорт подменяется наследником, сеть не используется.
5. Пример конфига включения — в docblock класса и в
   [admin/providers.md](../help/admin/integrations/providers.md).
6. Ядро, `layouts/view.php` и карточки объектов **не трогаются**.
